### 已确认的硬事实修正（重要，后续改文档必须用）

- **"Liquid 单页 for 循环 50 是平台硬限"是错的**：`for` 默认上限 50，但 `paginate` 单页 1–250、深度 25,000。50 只能是产品性能闸，不能写成平台限制。
- **集合 25,000 写错对象**：25,000 是 paginate 深度；原生筛选在集合 >5,000 商品时直接不显示。
- **Page JSON 模板设置不跨页面共享**：四个 Page 共用 `page.compare.json` → 设置只能四组统一，需改为从 handle 派生或每页独立机制。
- **Liquid 不能按 product metafield 全店查商品**：`all_products` 限 20 handle/页，不能遍历；`where` 不支持 metafield。
- **CSV `URL handle` 规则**：文档 §3.5 说多变体行重复 handle，§5.9 却写"每行唯一"——自相矛盾。正确：非空、商品内重复、商品间唯一。
- **`list.product_reference` CSV 值格式**：官方为分号分隔的 GID 或 handle，非逗号。
- **storefront visibility 是筛选必需的结论过宽**：官方仅对 metaobject/swatch 筛选明文要求。

### 刘工提出的替代路径：记录 variant_id + 客户端接口取数 —— 结论：走不通

逐条否决原因（写入 SDD 时需作为"为什么不用客户端取数"的依据）：

1. **`/products/<handle>.js`、`/variants/<id>.js`、Cart AJAX 均不返回 metafields**。对比的正是 metafield，所以客户端取不到核心数据。（SDD §6.2.1 已记载此事实）
2. **Section Rendering API 也救不了**：Liquid 的 `request` 只有 6 个属性，**读不到任何自定义查询参数** → 服务端不知道该渲染哪几款。
3. **Predictive search `/search/suggest.json`** 的 `resources[options][fields]` 是固定白名单，无 metafield。
4. **Storefront GraphQL** 需要 token，主题不得硬编码凭据，也不得依赖第三方服务。
5. 唯一"间接传参"通道是筛选参数（`collection.products` 会反映 URL 筛选态），但要给每商品加唯一可筛键，机制绕且需 spike。

附带结论：**记录 variant_id 无意义**——对比只呈现产品级参数（P4），记 handle 足够，variant_id 只会让本地存储 schema 变复杂。

### 数据岛体积的真实量级（修正"会很大"的直觉）

列式编码 + 严白名单下，每商品约 100–140 字节（handle/title/url/图 URL/10–11 个短值）：
250 款 ≈ 25–35 KB 原始 → 估算 gzip 约 4–7 KB（**待 A4 实测，不得写死**）。比一张商品缩略图还小。真风险不是字节数，而是 **Liquid 循环 250 款 × 11 字段的渲染耗时**。

### A4 spike 重定义（取代原 A3）

在开发店建一个对比集合，实测 **60 / 120 / 250 三档**：① 数据岛原始与 gzip 体积 ② Liquid 渲染耗时（Theme Inspector）③ 该页 LCP 与 TBT。
由实测决定新增设置项 **「数据岛封顶 N 款」**的默认值；硬上限 = `paginate` 单页 250。超限部分显式降级（占位 + 产品页链接 + 移除按钮），禁止静默截断。排序键写明为集合默认排序（默认 best-selling）。
预算写成公式 `gzip ≈ 商品数 × 每商品字节`，实测后填系数，不写死 KB。

### 竞品调研：变体 vs 独立产品（2026-09-29 网络调研，支撑"对比对象 = 型号"决策）

**结论：OPE 行业几乎全是「独立 SKU」，对比粒度天然是配置级（型号级），不存在"同型号不同变体"那一层。**

已找到证据：

- **Yard Force USA（Shopify 站）**：`YF40vRX21-SP` 与 `YF60VRX21-SP-2Battery` 是两个不同 handle，各自**只有一个 variant**，无电池/deck 下拉。系列页 https://yardforceusa.com/collections/lawn-mowers
- **Yard Force UK**：34cm 与 37cm 是两条独立商品记录。 https://uk.yardforce.eu/collections/gr40-lawnmowers
- **Greenworks**：同 21" 机型，不同电池配置是不同 handle + 不同 MODEL#（2546202 / 2546402）
- **Ryobi**：RY40180-Y、RY401120-Y、RY40LM30 各自独立页
- **Toro**：deck 21/22/30 in 分别是 MODEL 21327/21465/21219 独立页，站内还有「Add to compare」
- **EGO**：LM2135SP / LM2156SP / LM2206SP / LM2236SP / LM2244SP-2 并列，`-2`（含两块电池）是独立型号而非选项
- **Home Depot**：对比提示 "Select 2 to 4 Items to Compare"，卡片带 `Model#`——与我们"上限 4"一致
- **Amazon**：变体 = parent-child ASIN，child 才是可买单位；官方规则要求变体族内**非变化属性必须一致**、功能根本不同不能成族

反方证据（必须写进取舍）：

- **Shopify 官方偏「合」**：2048 变体博客把"拆成多商品页"称为过去的 workaround，主张集中到单一 PDP 与单一 canonical URL。https://shopify.com/id/blog/2048-variants
- **第三方 SEO 建议偏「按搜索意图分」**：各配置有独立搜索量 / 独立图片 / 独立用例时应拆成独立产品
- **Shopify 对比类 App**：默认 product 级；Snap Compare（Built for Shopify）等头部 App 已支持 variant 级对比与 metafields——即"变体级对比"在生态里存在，但依赖 App，我们不能依赖
- **未验证项**：EGO 官网是否用变体下拉未拿到真实商品页；App 能否读 **variant 级** metafield 各家未明说

对我们决策的含义：

1. "对比对象 = 型号"与行业惯例一致，不需要变体级对比也能对齐 Home Depot / Amazon / 所有 OPE 品牌。
2. 但要在商家文档里明说这条与 Shopify 官方"集中到单一 PDP"的建议相反，并给出理由：OPE 的核心规格（电压平台、deck 尺寸）会同时改变筛选维度、配件兼容与售后口径。
3. 新发现机制：**Combined Listings**（仅 Plus/Enterprise，主题 15.0.0+，上限 60 子产品）可让多个独立产品在店面上表现为变体切换，且每个 child 保留自己的 title/description/唯一 URL/图库。本主题面向非 Plus 商家，v1.0 不可用，但可作为商家文档里的"高端商家可选路径"提及。
4. 上限 4 款与 Home Depot 口径一致，可保留。

## 2026-09-29 追加：Section Rendering API 事实修正（重要，直接推翻我此前的笼统结论）

### 我此前说错的一句（必须修正）

我说"Section Rendering API 也救不了，因为 Liquid 读不到任何查询参数"。**这句过宽，是错的。** 正确表述：

- **任意自定义查询参数**：Liquid 确实读不到（`request` 只有 6 个属性：design_mode / host / locale / origin / page_type / path / visual_preview_mode）。
- **但平台保留参数会改变渲染上下文**，Liquid 通过特定对象感知：
  - `variant=<id>` → `product.selected_variant`
  - **`option_values=<id1>,<id2>` → `product_option_value.selected` + `product.selected_or_first_available_variant`**
  - `q` / `page` / `selling_plan` 同样有效

官方：https://shopify.dev/docs/storefronts/themes/product-merchandising/variants
> "You can also deep link using the format `?option_values=[option-value-id-1],...,[option-value-id-N]`… One option value ID must be provided per product option and the order must match the option order. If the option value combination maps to a variant that is not present, `selected_variant` and `selected_or_first_available_variant` will return null."

### Dawn 的实际写法（已核对源码）

- 参数名是 **`option_values`（复数，逗号分隔）**，不是 `option_value`。来源是 `product_option_value.id`。
- `assets/product-info.js` 的 `buildRequestUrlWithParams()`：`section_id=${this.sectionId}&option_values=${optionValues.join(',')}`
  https://github.com/Shopify/dawn/blob/main/assets/product-info.js
- 旧版 Dawn v13.0.1 曾用 `?variant=${id}&section_id=...`。
- 服务端应优先用 `selected_or_first_available_variant`；组合不存在时两者皆 null，**必须做 nil 兜底**。
- 文档冲突需注意：variants 页要求"按 option 顺序全传"，support-high-variant 页说"任意顺序、可部分传"。**按"顺序全传"写码。**

### Section Rendering API 参数（官方）

https://shopify.dev/docs/api/ajax/section-rendering
- `section_id`：**只能单个**，返回纯 HTML，不存在的 ID 返回 404
- `sections`：**最多 5 个**，逗号分隔或 `sections[]=a&sections[]=b`，返回 JSON
- "Any query parameters that are respected when rendering the full page, such as `q` or `page`, are also respected when sections are rendered."
- "You can't specify section setting values through the Section Rendering API."

### 变体级 metafield：仍不支持 CSV，且官方自相矛盾

- **CSV：仍不支持**（官方原文 "Variant metafields aren't supported for product CSV import/export."）。批量途径只有：后台「变体批量编辑器 + 添加 metafield 列」、GraphQL `metafieldsSet`（单次 ≤25 条）、`productVariantsBulkUpdate`、Bulk Operations、Flow 动作。
  https://help.shopify.com/en/manual/products/import-export/using-csv
- **能否在前台展示：两处官方文档直接冲突** —— API 文档称 "`storefront` 设置不影响 Liquid，metafields 在 Liquid 中总是可访问"，帮助中心却仍写 "At this time, product variant metafields can't be displayed to customers."。**上线前必须实测确认。**
- 动态数据源通常选不到 variant metafield（社区证据，非官方），需自定义 Liquid + SRA 重渲染。

### 对"对比页能否取变体数据"的结论

- **一次 SRA 请求 = 一个 URL = 一个 `product` 上下文**，`option_values` 只作用于该产品。跨产品只能逐个请求（同一产品内可用 `sections=a,b` 一次拿最多 5 个 section）。
- 因此"用 SRA 拿 N 款对比产品的变体" = **N 次请求**，每次返回的是完整 section 富 HTML（含图、价格块等），冗余字节需实测。
- **分两种需求，结论不同**：
  1. 只要变体**原生**字段（价格、可用性、SKU、变体标题、变体图）→ SRA 可行，成本是 N 次请求 + 富 HTML 冗余。
  2. 要变体级**规格**（metafield）→ 卡在**录入**：CSV 不支持，只能走批量编辑器 / GraphQL，等于放弃"CSV 批量导入"这个 P0 卖点。
- 待刘工确认他到底要哪一种，再决定是否在 SDD 里新增变体列方案。
